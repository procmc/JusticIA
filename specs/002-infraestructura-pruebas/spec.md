## Contexto y objetivo

La constitución (principio 4) y RA-02 exigen que cada requisito se cubra con pruebas automatizadas (unitarias, de integración y de extremo a extremo), escritas antes del código y además de la verificación manual. El código heredado no tiene ninguna, y el «Estado actual» de RA-02 lo dice: «la suite de pruebas automatizadas todavía no existe».

Esta spec construye la **infraestructura de pruebas del backend**, de forma mínima: una base de datos y una colección de Qdrant solo para pruebas, en los mismos servicios que ya corren; una protección que impide que la suite toque los datos de desarrollo; un comando único; y piezas simuladas para lo que no es determinista (el modelo de lenguaje, el reconocimiento de escritura, la transcripción de audio y el correo). No escribe las pruebas de ningún módulo. Orden de `.claude/rules/testing.md`:

1. **Esta spec (002)**: infraestructura del backend.
2. La red de seguridad de los flujos críticos (inicio de sesión y roles; subir un archivo → Procesado → el chat lo cita; NotebookServIA), que hereda el extremo a extremo (ver «Fuera de alcance»).
3. Las specs retroactivas por módulo, según riesgo.

La meta es **al menos una prueba automatizada por requisito del ERS**, no el 100 % de cobertura de líneas (RA-02). Plazo estimado: de dos a tres días de trabajo.

**Por qué importa el aislamiento**: el sistema lee su configuración con `load_dotenv()` en cinco módulos (el de configuración, el de Alembic, la migración consolidada, el servicio de correo y la ruta de correo), que **no sobrescribe** una variable ya definida, y crea la conexión a SQL Server en cuanto se importa. Sin una protección explícita, una suite escrita con el código tal como está apuntaría a la base de datos de desarrollo y a su colección de Qdrant.

**Contexto de desarrollo**: el sistema solo corre en desarrollo y no tiene datos institucionales. Por eso la spec no protege contra dos corridas a la vez (hay una sola) ni usa un contenedor aparte; protege contra el error propio: apuntar sin querer a la base o a la colección de desarrollo.

**Límite documentado — la spec 003 (corrección del correo)**: Andrés quiere que esta infraestructura sirva a la spec 003 (RF-02 y RF-03: el reseteo por el Administrador no debe cambiar la contraseña si el correo falla; la recuperación por código mantiene la respuesta genérica y avisa al Administrador). Por eso esta spec deja listo el **envío de correo simulado** que falla a voluntad (RA-02.6) y el soporte de pruebas de regresión y de fallos esperados (RA-02.1). No corrige ni prueba el comportamiento del correo.

**Límite documentado — RNF-08 («Estado actual»)**: el servidor todavía acepta contraseñas de 6 caracteres, aunque el requisito pide 8. Las contraseñas de prueba tienen al menos 8 caracteres (RA-02.7) y esta spec no prueba esa validación; eso es de la spec retroactiva de autenticación.

## Definiciones
- **Comando único**: `docker compose exec backend pytest`, que corre toda la suite (unitarias e integración) dentro del contenedor `backend` que ya está en uso. Subconjuntos, por marcador: **unitarias** (sus pruebas no usan ningún servicio; aun así la base de pruebas se crea al inicio, RA-02.4) e **integración** (con SQL Server, Qdrant y Tika reales).
- **Marcador `infraestructura`**: el de las pruebas que producen a propósito un fallo, un XPASS o un error de preparación, o que lanzan una segunda corrida, para verificar el resumen, el aborto y el ciclo de vida. **No** forman parte del comando único por omisión. Se ejecutan con un comando explícito, `docker compose exec backend pytest -m infraestructura`, y su resultado esperado es el que producen a propósito (RA-02.1).
- **Nombre de pruebas** (se distingue mayúsculas de minúsculas, el nombre **completo** debe coincidir): `servia_pruebas`. Es el nombre de la base de datos y de la colección de Qdrant de pruebas.
- **Prefijo `PRUEBA`**: el de los datos que crea una prueba (usuarios, notebooks, archivos), como indica `.claude/rules/testing.md`.
- **Datos de desarrollo**: la base de datos, la colección de Qdrant, el Redis y la carpeta `uploads/` que usa el sistema al correr.
- **Configuración que define la suite**: los valores de las variables de entorno que fija la propia suite antes de importar el código del sistema (RA-02.2).
- **Simulado**: una pieza falsa que responde con lo que la prueba le indica y registra qué se le pidió. Nunca abre una conexión real.
- **Prueba humo**: la prueba mínima de cada tipo que demuestra que la infraestructura funciona; no cubre un requisito de ningún módulo.
- **Entorno limpio**: la máquina después de reconstruir la imagen del backend y de arrancar los servicios desde cero, sin datos ni archivos de pruebas anteriores.

## Requisitos funcionales

- RA-02.1 `[NUEVO]` (detalla RA-02, RA-01; principio 1): EL SISTEMA DE PRUEBAS corre toda la suite del backend con el **comando único**, con marcadores que permiten correr solo las unitarias o solo las de integración, sin servicios nuevos ni cambios en `docker-compose.yml`. AL terminar cada corrida imprime un resumen en español con seis contadores: pruebas que **pasan**, que **fallan**, **fallos esperados** (xfail), fallos esperados que **pasan** (XPASS), **errores de preparación** y **omitidas** (con su motivo). La corrida termina con éxito solo si no hay fallos, ni XPASS (un fallo esperado que pasa hace fallar la corrida, para que se quite su marca), ni errores de preparación; las omitidas se muestran pero no la hacen fallar. Marcar una prueba como fallo esperado exige la referencia al requisito que el código aún no cumple. Que cada prueba nombre el requisito que cubre (por ejemplo, `RF-19.1`) es una **convención** de `.claude/rules/testing.md`, no una condición que haga fallar la corrida. `pytest` entra a `requirements.txt` y a `Dockerfile.prod`: es una decisión del plan, que la justifica (principio 1).
  - *Cómo se comprueba*: (a) en un entorno limpio, el comando único termina con éxito y el resumen muestra los seis contadores; (b) cada subconjunto corre solo las pruebas de su tipo (el número recolectado por marcador) y el comando único no recolecta ninguna prueba del marcador `infraestructura`; (c) el comando explícito `pytest -m infraestructura` corre pruebas de ejemplo que producen, a propósito, un fallo esperado que falla (no cuenta como fallo), un XPASS, una omitida con motivo, un error de preparación y un fallo. Su resultado esperado es un resumen con **1 fallo esperado, 1 XPASS, 1 omitida, 1 error de preparación y 1 fallo**, y un código de salida distinto de cero; cualquier otro resumen indica que el informe no cuenta bien; (d) `docker compose config --services` muestra los mismos ocho servicios que antes y `docker compose ps` no muestra reinicios (verificación concreta del revisor, RA-02.8).

- RA-02.2 `[NUEVO]` (RNF-09, RT-02; principio 5): ANTES de importar cualquier módulo del sistema, EL SISTEMA DE PRUEBAS **fija por sí mismo** la configuración que decide a qué datos y a qué servicios apunta el código, de modo que las llamadas a `load_dotenv()` no la sobrescriben. SI algún módulo del sistema ya está importado cuando la suite va a fijar la configuración, ENTONCES aborta, porque esos módulos ya habrían leído el entorno real. Debe fijar como mínimo:
  - Nombres de datos: `SQL_SERVER_DATABASE` y `QDRANT_COLLECTION_NAME` (el nombre de pruebas), y `REDIS_URL` con una dirección que no resuelve a ningún servidor (las pruebas nunca se conectan al Redis real, RA-02.5).
  - Seguridad: `JWT_SECRET_KEY` (aleatoria por corrida) y los datos del administrador que siembra la migración consolidada: `ADMIN_CEDULA`, `ADMIN_USERNAME`, `ADMIN_EMAIL`, `ADMIN_PASSWORD` (aleatoria por corrida, sin la contraseña por omisión de la migración), `ADMIN_NOMBRE` y `ADMIN_APELLIDO`.
  - Correo: `EMAIL_PROVIDER`, `EMAIL_USERNAME`, `EMAIL_PASSWORD`, `EMAIL_HOST`, `EMAIL_PORT` y `EMAIL_USE_TLS`, con valores inventados.
  - Servicios simulados: `OLLAMA_BASE_URL`, `OLLAMA_MODEL`, `OLLAMA_API_KEY` y `HTR_SERVER_URL`, con direcciones que no resuelvan a ningún servidor real, para que una llamada accidental falle.
  - Audio: `ENVIRONMENT`, `WHISPER_MODEL`, `WHISPER_DEVICE`, `WHISPER_COMPUTE_TYPE`, `WHISPER_NUM_WORKERS` y `AUDIO_CHUNK_DURATION_MIN`.
  - Modelos: `EMBEDDING_MODEL` y `DIM`. El servidor de extracción de texto (`TIKA_SERVER_URL`) queda con el real, que solo usa la integración.

  Solo estos valores se toman de la configuración de desarrollo (el entorno del contenedor o `backend/.env`): el servidor, el puerto, el usuario, la contraseña y el driver de SQL Server (`SQL_SERVER_HOST`, `SQL_SERVER_PORT`, `SQL_SERVER_USER`, `SQL_SERVER_PASSWORD`, `SQL_SERVER_DRIVER`), y la dirección de Qdrant (`QDRANT_URL`). Con esas credenciales de administración se crea y se elimina la base de pruebas. SI falta alguno de ellos, ENTONCES la suite aborta y nombra la variable, sin usar un valor por omisión del código. Cualquier otra variable de `backend/.env` no tiene efecto sobre la suite.
  - *Cómo se comprueba*: (a) prueba unitaria que carga la configuración con un `.env` de ejemplo con valores distintos y comprueba que cada variable fijada por la suite conserva el valor de la suite; (a2) prueba unitaria con un módulo del sistema ya importado, que comprueba el aborto; (b) prueba que quita una de las variables de administración y comprueba el aborto con su nombre; (c) prueba que, sin ningún `.env`, la suite arranca con la configuración propia y aborta solo por lo que le falta de las variables de la segunda lista, con su nombre.

- RA-02.3 `[NUEVO]` (principio 5): SI la base de datos o la colección de Qdrant a la que apunta la suite no tiene el nombre de pruebas (el nombre completo, con mayúsculas y minúsculas), ENTONCES EL SISTEMA DE PRUEBAS aborta **antes de que el sistema abra ninguna conexión** y de ejecutar cualquier prueba, con un mensaje en español y un código de salida distinto de cero. La protección valida el **valor efectivo que el código ya tomó** (la URL de conexión a la base y el nombre de la colección tal como los usa el sistema), no solo lo que la suite escribió. No existe ningún parámetro ni variable que desactive la protección. Crear y eliminar bases de datos y colecciones pasa siempre por esta validación.
  - *Cómo se comprueba*: (a) **una** prueba unitaria que invoca la protección con un nombre inválido (el nombre de la base de desarrollo, el nombre de pruebas en mayúsculas y un nombre que solo contiene el nombre de pruebas), tanto como valor escrito como valor efectivo (por ejemplo, una URL de conexión con otra base), y comprueba que lanza el aborto antes de abrir una conexión, y que con el nombre exacto no aborta; (b) una prueba del marcador `infraestructura` que lanza una segunda corrida con un nombre inválido y comprueba que termina con código de salida distinto de cero y el mensaje en español, antes de conectarse.

- RA-02.4 `[NUEVO]` (RA-02; `.claude/rules/testing.md`): AL inicio de **toda** corrida, incluso si solo se piden las unitarias, EL SISTEMA DE PRUEBAS crea la base de datos de pruebas y le aplica **las migraciones de Alembic desde cero**, **antes** de importar el módulo que se conecta a la base (`database.py` lo hace al importarse, con hasta 10 intentos de 3 segundos). Así no hay una espera de unos 30 segundos ni queda el motor sin crear. En las corridas de integración crea además la colección de Qdrant de pruebas. AL terminar, **aunque haya pruebas que fallen**, elimina la base y la colección. SI una corrida anterior se cortó y dejó la base o la colección, ENTONCES la siguiente corrida las reemplaza, porque el nombre es el mismo: es un entorno de desarrollo y hay una sola corrida a la vez (dos corridas simultáneas no se soportan). SI SQL Server, Qdrant o Tika todavía no responden (por ejemplo, SQL Server tarda en arrancar), ENTONCES la suite espera y reintenta durante **60 segundos**, y SI se agota, ENTONCES aborta con un mensaje en español que dice qué servicio no respondió.
  - *Cómo se comprueba*: (a) prueba de integración que confirma que, durante la corrida, la base existe con el esquema de las migraciones y la colección existe; una corrida que pide solo unitarias también crea la base; (b) prueba del marcador `infraestructura` que deja una base de pruebas previa con una tabla de ejemplo y comprueba que la corrida la reemplaza; (c) prueba del marcador `infraestructura` que fuerza el fallo de una prueba; el revisor comprueba, **después** de esa corrida y desde fuera de pytest, que no quedan ni la base ni la colección de pruebas; (d) prueba unitaria del mecanismo de espera con un servicio simulado que responde al tercer intento y con otro que nunca responde en 60 segundos simulados (el mensaje nombra el servicio); (e) verificación manual, tras una corrida: la base y la colección de pruebas no existen y los conteos de filas y de puntos de los datos de desarrollo son los mismos que antes.

- RA-02.5 `[NUEVO]` (RA-02, principio 5): MIENTRAS corre la suite, EL SISTEMA DE PRUEBAS **nunca** usa la carpeta `uploads/` de desarrollo: usa una carpeta temporal propia, que elimina al terminar. Las pruebas **nunca se conectan al Redis real**: Redis se simula siempre, en unitarias y en integración (el mecanismo exacto lo decide el plan). Las tareas de Celery se ejecutan de forma inmediata dentro del proceso de pruebas, sin publicarse en ninguna cola, de modo que el worker real nunca consume una tarea de prueba.
  - *Estado actual*: la suite **desvía las rutas** de archivos y de avatares del sistema a la carpeta temporal, pero el guardado real de un archivo fuera de la carpeta del backend (`/app`) hoy falla, porque `guardar_archivo` calcula una ruta relativa a esa carpeta (`relative_to`). Por eso esta spec no prueba el guardado real; probarlo, y corregir `guardar_archivo`, corresponde a la futura spec de ingesta (retroactiva), con su prueba de regresión.
  - *Cómo se comprueba*: (a) prueba unitaria que comprueba que las rutas de archivos y de avatares del sistema apuntan a la carpeta temporal durante la suite y se restauran al terminar (solo el desvío de rutas); (b) prueba que dispara una tarea de ingesta y comprueba que se ejecutó dentro del proceso y que el cliente de Redis que usó el código es el simulado; (c) verificación manual, tras una corrida: el contenido de `uploads/` y el número de claves del Redis de desarrollo son los mismos que antes.

- RA-02.6 `[NUEVO]` (RNF-09, RT-02; `.claude/rules/testing.md`, «LLM»): EL SISTEMA DE PRUEBAS ofrece simulados de Ollama, del servidor de reconocimiento de escritura y de la transcripción de audio (faster-whisper), cada uno con respuestas definidas por la prueba y con registro de lo recibido. Ofrece un **envío de correo simulado** que (a) puede fallar a voluntad, (b) registra qué mensajes se intentaron enviar, a quién y con qué contenido, y (c) hace observable el fallo al código que se prueba. Redis se simula siempre (RA-02.5). En las **unitarias** también se simulan SQL Server, Qdrant, Tika y el modelo de embeddings; en las de **integración** son reales SQL Server, Qdrant, Tika y el modelo de embeddings. Que Ollama, el reconocimiento de escritura, la transcripción de audio y el correo no sean reales se garantiza de dos maneras, y **no** con una comprobación global al iniciar la sesión: (1) cada simulado lleva su propia comprobación, que se ejecuta cuando una prueba lo pide: SI el cliente que usa el código del sistema no resulta ser el simulado, ENTONCES la suite aborta y nombra cuál; (2) las direcciones de esos servicios apuntan a nombres `.invalid` (RA-02.2), que no resuelven a ningún servidor, de modo que una prueba que no pida el simulado y haga una llamada accidental falla en vez de llegar a un servicio real. Las pruebas del LLM comprueban la **estructura** de la respuesta, no el texto; la calidad real del LLM no se automatiza (exención del principio 4, con verificación manual).
  - *Cómo se comprueba*: (0) prueba unitaria que comprueba, para cada uno de los cuatro, que con su simulado instalado el cliente que usa el código es el simulado, y que el aborto ocurre si no lo es; (a) prueba humo unitaria: con Ollama simulado, un flujo de consulta usa la respuesta definida y registra la pregunta; (b) prueba humo unitaria del correo: con el envío simulado configurado para fallar, se ejecuta el envío real del sistema y se comprueba que el intento quedó registrado y que el fallo llegó al código (no se comprueba cómo reacciona el sistema: es la spec 003); (c) prueba humo de integración: la API rechaza una petición sin token (RNF-07) y un fragmento de texto inventado se guarda y se recupera en la colección de pruebas con el modelo de embeddings real; (d) prueba unitaria del guardián de las unitarias: una prueba unitaria de ejemplo que intenta usar Qdrant, SQL Server o Tika reales y atrapa el error que se le lanza **igualmente falla al cerrarse**, y el mensaje nombra el servicio (el guardián no depende de que el código del sistema deje pasar la excepción).

- RA-02.7 `[NUEVO]` (RNF-07, RNF-08, principio 5; `.claude/rules/testing.md`, «Datos de prueba»): CUANDO una prueba necesita usuarios, EL SISTEMA DE PRUEBAS crea un **Administrador** y un **Usuario Gubernamental** inventados, con el prefijo `PRUEBA`, una contraseña de **al menos 8 caracteres**, distinta y aleatoria en cada corrida, guardada con hash como en el sistema real, y con `CF_Ultimo_acceso` lleno para que no se les obligue a cambiar la contraseña. El administrador que siembra la migración consolidada no se usa en las pruebas (su contraseña es aleatoria y nadie la conoce). Las contraseñas no se escriben en ningún archivo ni se muestran en la salida, los informes o los registros. Los archivos de prueba los genera la suite con contenido inventado, nunca documentos institucionales ni datos personales. AL terminar **cada prueba**, EL SISTEMA DE PRUEBAS limpia lo que esa prueba creó: sus filas (usuarios, notebooks, documentos y registros de bitácora propios), sus puntos en la colección de pruebas, sus claves y sus archivos. **No** toca los catálogos que siembran las migraciones (roles, estados, tipos de acción). Ninguna prueba depende de lo que dejó otra, así que se pueden correr en cualquier orden y por separado. El borrado físico vale solo en la base y la colección de pruebas (RA-02.3).
  - *Cómo se comprueba*: (a) prueba humo de integración: cada usuario inicia sesión con el rol esperado sin que se le pida cambiar la contraseña, y la contraseña guardada no es el texto plano; (b) **sin depender del orden**: al terminar la sesión de pruebas (antes de eliminar la base), una comprobación cuenta las filas, los puntos de la colección y los archivos con prefijo `PRUEBA` y el resultado debe ser **cero**, y los catálogos de las migraciones siguen completos; (c) la suite corrida con el orden invertido da el mismo resultado; (d) una búsqueda de la contraseña en el repositorio y en la salida de la corrida no la encuentra (verificación manual).

- RA-02.8 `[NUEVO]` (RA-02, RA-01; principio 2): AL cerrar la spec se actualiza la documentación afectada. Estas comprobaciones **no son pruebas de pytest** (el contenedor del backend no ve `docker-compose.yml`, `CLAUDE.md`, el hook del revisor ni el ERS). Son verificaciones concretas que **ejecuta el revisor durante `/sdd-validate`** y que quedan en su informe. Es una **exención al principio 4 aprobada expresamente por Andrés (05–06/10)**.
  - `CLAUDE.md` («Comandos» y «Verificación») recoge el comando único y los de cada subconjunto, y su sección «Datos» refleja la excepción del borrado de datos de prueba.
  - `docs/constitution.md` (principio 5) y `.claude/rules/testing.md` reflejan esa excepción y que las contraseñas de prueba las genera la suite y no se escriben ni se muestran, y el resto de `testing.md` queda coherente con esta spec.
  - El permiso del revisor para el comando único en `.claude/hooks/validate-bash.sh`: debe dejar pasar `docker compose exec backend pytest` y sus subconjuntos.
  - El ERS (RA-02 en 2.4.3, en sus versiones Word y PDF) cambia su «Estado actual» a «la infraestructura de pruebas del backend existe; la cobertura sigue siendo progresiva; el extremo a extremo llega con la spec de la red de seguridad», y se propone un párrafo que describa el entorno de pruebas.
  - *Cómo se comprueba*: (a) cada comando documentado se copia tal cual y se ejecuta con éxito; (b) se alimenta el hook del revisor con el JSON de cada comando documentado y lo deja pasar (código de salida 0), y con un comando de borrado cualquiera lo bloquea; (c) una búsqueda de texto confirma que las tres reglas contienen la excepción aprobada; (d) una lectura del ERS confirma que RA-02 ya no dice que la suite no existe.

## Requisitos no funcionales
Ninguno aparte: los atributos de calidad (aislamiento, informe en español, simulados) están expresados como requisitos numerados, porque cada uno es medible.

## Casos límite
Cada uno está cubierto por un requisito con su comprobación:
- `backend/.env` ausente o con otros valores: RA-02.2.
- La suite apunta a la base o a la colección de desarrollo: RA-02.3.
- SQL Server, Qdrant o Tika todavía arrancando: RA-02.4 (espera de 60 segundos, y la base de pruebas se crea antes de importar `database.py`).
- Un módulo del sistema ya importado antes de fijar la configuración, o un valor efectivo que apunta a otra base: RA-02.2 y RA-02.3.
- Corte que deja una base o una colección huérfanas: RA-02.4 (la siguiente corrida las reemplaza; hay una sola corrida a la vez).
- Dos corridas a la vez: no se soportan (RA-02.4).
- Archivos, claves o tareas de prueba que lleguen al sistema real: RA-02.5.
- Los datos de prueba aparecen en informes, registros o en el repositorio público: RA-02.7.

## Fuera de alcance
- **Pruebas de extremo a extremo** (Playwright, la instancia de pruebas del backend y del frontend y las contraseñas de prueba hacia el navegador): pasan a la **spec de la red de seguridad**, que hereda de esta el comando único, el nombre de pruebas y su protección (RA-02.3), la configuración propia (RA-02.2), los usuarios de prueba por rol con sus contraseñas generadas por corrida (RA-02.7, con la decisión de cómo entregarlas al navegador sin escribirlas ni mostrarlas) y los simulados (RA-02.6). Esa spec define también la protección de la instancia a la que apunte el navegador, una prueba humo de inicio de sesión en escritorio y en pantalla pequeña (RNF-04) y el lugar donde corre el navegador.
- Contenedor aparte y perfil `pruebas` en `docker-compose.yml`, Redis aparte, bloqueo de red, nombres únicos por corrida, comando de limpieza de huérfanas y corridas simultáneas.
- Las pruebas de cada módulo y la red de seguridad de los flujos críticos; aquí solo hay pruebas humo y las del resumen.
- El guardado real de un archivo subido en la carpeta temporal (RA-02.5) y la corrección de `guardar_archivo`, que hoy falla fuera de `/app`: futura spec de ingesta (retroactiva).
- Una comprobación global, al iniciar la sesión, de que todos los simulados están instalados (RA-02.6): la garantía es la de cada simulado más las direcciones `.invalid`.
- La corrección del correo y sus pruebas (spec 003): aquí solo el envío simulado y el soporte de pruebas de regresión.
- Pruebas unitarias del frontend con un ejecutor de JavaScript: no se agregan dependencias al frontend.
- La cobertura de líneas como objetivo (skill `pytest-coverage`): solo es un indicador.
- Pruebas de rendimiento, de carga o de calidad real del LLM; el aspecto visual (exención del principio 4); la validación de contraseñas de 8 caracteres (RNF-08); y reescribir código heredado que no tenga relación con la infraestructura.

## Criterios de finalización
- En un entorno limpio, `docker compose exec backend pytest` corre toda la suite y termina con éxito: pasan la prueba humo unitaria y la de integración (RA-02.6, RA-02.7), la prueba de la protección (RA-02.3) y las del resumen (RA-02.1).
- Tras la corrida, la base, la colección y la carpeta temporal de pruebas ya no existen, y los datos de desarrollo no cambiaron (conteos de filas y de puntos, claves de Redis y contenido de `uploads/`): verificación manual.
- Cada requisito de RA-02.1 a RA-02.7 tiene al menos una prueba automatizada que pasa (RA-02.5 comprueba el desvío de rutas, no el guardado real de archivos; ver «Fuera de alcance»). Las exenciones son solo dos: lo que no se puede medir de forma fiable (la calidad real del LLM, RA-02.6) y la **exención aprobada por Andrés (05–06/10)** para RA-02.8: las verificaciones de configuración y documentación (`docker-compose.yml`, `CLAUDE.md`, el hook del revisor y el ERS) no son pruebas de pytest, las ejecuta el revisor durante `/sdd-validate` y quedan en su informe. Las comprobaciones manuales contra los datos de desarrollo se suman a las pruebas, no las reemplazan.
- El comando explícito `pytest -m infraestructura` produce el resumen esperado de RA-02.1 (1 fallo esperado, 1 XPASS, 1 omitida, 1 error de preparación y 1 fallo, código de salida distinto de cero); no forma parte de la corrida «todo verde» del comando único.
- `docker compose ps` no muestra reinicios y los ocho servicios arrancan como antes.

## Riesgos para el plan (no cambian el QUÉ)
- Memoria del contenedor `backend` si, en integración, se carga el modelo de embeddings (~3 GB) mientras el backend ya tiene el suyo cargado (el contenedor tiene un límite de 6 GB).
- Los archivos que escriba la suite (carpeta temporal, caché de pytest, `__pycache__`) no deben disparar el `--reload` del backend real, que vigila `/app`.
- **O1 (guardián de SQL Server)**: como la base de pruebas se crea al inicio de toda corrida (RA-02.4), el módulo que se conecta a la base queda importado en cada corrida, así que el bloqueo del guardián de las unitarias por importación de ese módulo deja de activarse; solo queda el bloqueo de la conexión al conector de SQL Server. Al integrar la base de pruebas, el plan debe comprobar que el guardián sigue frenando una conexión real a SQL Server desde una unitaria (RA-02.6 d).
- El mecanismo exacto con el que se simula Redis (RA-02.5), el texto exacto de los comandos de subconjuntos, y la justificación de que `pytest` entre a `requirements.txt` y a `Dockerfile.prod` (RA-02.1, principio 1).
